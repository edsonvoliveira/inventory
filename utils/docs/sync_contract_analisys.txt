Analise de Contrato de Sync (teorico vs implementado)

0) Contrato global (vale para todas as entidades sincronizadas)

TEORICO (sync_contract.txt)
- Campos obrigatorios no INSERT: nao definido por campo; regra global: uuid gerado no client e idempotencia por uuid.
- Campos mutaveis no UPDATE: nao definido por campo; regra global: update permitido respeitando conflito (LWW por updated_at).
- Soft delete: nao hard delete; usar deleted_at e/ou is_active; pull deve incluir deletados.
- Origem permitida: company_id sempre filtrado no server (RLS); mobile nao escreve entidades administrativas.
- Pull (filtros/since): since em ISO 8601 UTC; retorno de updated_at > since (ou >=); incluir deletados.
- O que isso indica para o contrato: cada entidade deve ter lista explicita de campos e regra de conflito por updated_at.
- Sugestao de formato de contrato (exemplo textual):
  "Regra global: uuid do client; push idempotente por uuid; pull incremental por updated_at (UTC) incluindo deletados; conflito LWW com server como fonte".

HANDLERS
- Nao ha handler unico global; as regras estao dispersas nos handlers de cada entidade.
- Campos obrigatorios no INSERT: definido por handler (varia por entidade).
- Campos mutaveis no UPDATE: definido por handler (varia por entidade).
- Soft delete: definido por handler (is_active, deleted_at, is_blocked, ou nao suportado).
- Origem permitida: em geral company_id e user_id sao server-side quando o handler fixa no payload.
- Pull (filtros/since): cada handler implementa filtro e since; gte(updated_at) em UTC; alguns fazem join para filtrar por company_id.
- O que isso indica para o contrato: o contrato global nao esta centralizado nem validado; risco de inconsistencias entre entidades.
- Sugestao de formato de contrato (exemplo textual): "Cada handler deve declarar allowlist de update e padrao de soft delete; nao aceitar company_id do client".

REPOSITORIES (app_core)
- Nao ha repositorio global; cada entidade tem um RepoPort com upsert_many.
- Campos obrigatorios no INSERT: n/a (repositorios apenas aplicam upsert).
- Campos mutaveis no UPDATE: n/a.
- Soft delete: n/a.
- Origem permitida: n/a.
- Pull (filtros/since): n/a no app_core; aplica payload recebido do backend.
- O que isso indica para o contrato: o enforcement do contrato nao ocorre no app_core; fica no backend e nas validacoes de UI.
- Sugestao de formato de contrato (exemplo textual): "Repositorios locais aceitam payload do server e fazem upsert; validacao deve ocorrer antes".

ANALISE
- Regra global de idempotencia nao aparece nos handlers (nao ha UPSERT por uuid no backend).
- Conflito LWW por updated_at nao esta implementado nos handlers.
- Soft delete varia entre entidades (is_active vs deleted_at vs is_blocked), sem padrao consistente no codigo.

IDEMPOTENCIA POR ENTIDADE (resumo)
- Regra geral: UUID e a chave idempotente em todo PUSH; insert/update devem ser UPSERT por uuid.
- companies/users: update limitado; reenvio nao deve alterar estado nem gerar efeitos colaterais.
- master data (products, categories, barcodes, locations): reenvio por uuid nao duplica.
- inventory_events/zones/targets: reenvio por uuid nao duplica.
- zone_user_progress: reenvio nao duplica progresso.
- inventory_items: reenvio nao cria item duplicado; update repetido nao gera eventos duplicados.
